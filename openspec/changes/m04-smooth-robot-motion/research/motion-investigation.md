# 探索机器人移动与轻惯性只读调研

2026-11-17，motion_research。仅源代码与原始技术资料研究，没有运行Godot、ADB、模拟器、Docker或性能采样，没有修改产品、测试入口或任务勾选。本文件不构成实现许可。

## 一 结论与适用基线

玩家看到的“一顿顿”和“拐弯折线”至少涉及三个不同层次：服务器状态采样与客户端呈现、合法路径形状、机器人沿路径的速度和朝向。当前源已证明后两者以及第一层中的呈现机制存在生硬因素；还不能仅凭代码判定这台手机的网络抖动、帧率、服务器tick耗时分别贡献多少。

建议先诊断并修正客户端快照呈现和朝向，再在服务器的现有安全合同内做路径跟随平滑，最后评审加减速参数。借鉴赛车的输入变化率、速度相关转向和前视跟随，不引入赛车轮胎、悬挂、漂移或整套车体物理，也不把当前格网导航全换成NavMesh。

对照已交付 `build/private-beta/snapshots/rc-1082-auto-replan/game/`：下表所涉Unit、Sim、Field、Expedition、Camp、Treasure、Solo、Catalog、client/unit_view均与工作区同字节；`net/party.gd`存在既有ACK差异，不能把工作区ACK变化当本次运动改动。实际部署必须继续单列客户端2345与服务端366e来源，不声称同一manifest。

## 二 当前调用链与已证事实

### 2.1 模拟、发送与显示不是同一频率

| 层／模式 | 当前实现和定位 | 可得结论与限制 |
|---|---|---|
| Godot服务器模拟 | `deploy/server.godot:12`设置20 physics ticks/s；`Dockerfile:12–16`复制该配置及Sim到服务镜像 | 20Hz是模拟节拍，不等于每秒20份网络位置快照 |
| Solo探索 | `game/net/solo.gd:323–350`每physics步推进，普通delta发送门限`sync_time>=0.12`；阶段变更可发full | 名义门限约8.3Hz，但20Hz步长会量化发送时刻，通常可能约0.15s；实际到达间隔须记录，不能把门限倒数冒实测 |
| 常规合作／泵站／工厂 | `game/net/party.gd:190–250`普通delta门限0.15s；阶段／集合／落盘约束另行影响发布 | 名义约6.7Hz，且存盘失败可能暂缓推进／发布。不能靠客户端滤波隐藏真正的服务器停顿 |
| 公开营地 | `game/net/camp.gd:223–262`普通delta门限0.2s | 名义约5Hz，不是20Hz位置广播 |
| 秘宝 | `services/profile/treasure_combat.py:7`固定STEP0.25；`game/net/treasure.gd:109–131`每0.25s查frames | Python权威250ms离散步长与约4Hz桥接，独立于Godot Sim，不可套用探索服务器改动并宣称秘宝也已改善 |
| 客户端状态接收 | `net/solo.gd:703–733`覆盖最新位置／heading／walking；`net/treasure.gd:148–156`只接受较新tick/seq后覆盖state | 已有旧包拒绝和权威状态边界，但没有可见的历史快照时间缓冲 |

### 2.2 视觉位置与朝向

- 探索 `game/expedition/expedition.gd:797–825,990–1000`：接包更新targets；每渲染帧`u.pos.lerp(row.pos,min(delta*16,1))`。这是追赶最新目标点的低通，不是按服务器时间在两份快照之间重建位置。到新点后速度大、接近时变慢，低频快照容易出现周期性追赶观感。
- 营地 `game/camp/camp.gd:576–602`同样使用`delta*16`追点。秘宝 `game/treasure/treasure.gd:349–366`用`delta*12`；它还根据与最新点的距离是否大于0.04设置walking，因而有近点后动画切回Idle、下一包再Move的可能。这一动画抖动目前是源上风险，未做运行复现。
- `game/battle/unit.gd:75–85,114–116`把传入呈现位置直接写Node3D，heading变化时直接赋`robot.rotation.y`，没有角速度过渡。服务器非盾板机体的heading也会瞬转，两个层面要分开。
- 试车台 `game/client/unit_view.gd:27–37`已有指数形式的帧率独立位置／角度趋近，但它只服务试车台，不能据此声称探索已经具有相同实现；追最新点的指数趋近也不能代替快照时间缓冲。
- `game/assets/steam_crawler/robot.gd:253–265`的set_motion只在动画名变化时play，Attack/Death有明确优先；可复用这些宿主入口，不应在每帧手动重启Walk动画。屏外姿态冻结／补进度合同在同文件234–251，不能为平滑随意删掉。

### 2.3 路径与运动

- `game/battle/field.gd:9,18,45–83`只有四邻域，AStar禁止对角；实际movement的walk_region用带几何排除的四邻域搜索。`region_path:108–127`原样回溯格点，不做视线拉直、圆角或前视。
- `game/battle/simulation.gd:640–718`的_walk使用`remaining=move_speed*delta`，逐段消耗路径，可以在一个step跨多个点；没有单独速度／加速度状态，也没有“每到一个格点故意等待一帧”的实现。因此不能说顿挫必然是格点停走；可确认的是恒速与硬折线转向。
- `_turn:721–729`非盾板直接设置heading；带rivet_shield的机体按盾板的180度/s限制。`_hit:731–742`以该heading判正面减伤，朝向是战斗规则的一部分，不能把全部逻辑朝向挪成客户端装饰。
- `Catalog CHASSIS:9–85`现有履带3.6、双足4.6、两类轮式5.4最大移速及身体半径；目前没有每底盘独立加速度、制动距离或最小转弯半径参数。加上这些不是“只改动画”的等价修复。
- `_next_auto_replan_phase:524–528`及`_walk_region:530–539`已有0.5模拟秒、10相位错峰规则；这可能解释被阻挡时最长一段等待，但旧评审明确接受了性能／响应取舍。不能把所有间歇都归它，也不应直接删除节制或提高全图重算频率。

## 三 不得倒退的既有安全与架构合同

依据 `openspec/changes/m04-unit-movement-clearance/verification/root-auto-replan-development-review.md`、同目录`movement-performance-next-review.md`，以及归档M14的`root-exit-post-development-review.md`：

1. Sim持有权威位置、目标、路径、身体排除与指令原子规划，Field持纯几何；页面只显示和提交意图，不自己判到达、开火、伤害或胜负。
2. `_static_walk_segment`核bounds/solid/LOS；每step实际消费的段仍经`Field.safe_fraction`、身体半径、已接受扫段和`_escape_improves`。圆角不得切入门柱、石块、队友或目标身体；不能豁免钻头短射程接近。
3. 原路线缓存、requested_goal、0.5sim重规划期限属于已签状态；修改这些语义需复审。不是为了顺滑就恢复每tick全图寻路。
4. Exit实际门柱已进入权威足迹，不能用客户端曲线把机器人画进柱子，或移目标／放大撤离距离伪造通行。
5. 若加入会影响后续决策的velocity／turn状态，应和既有路径状态一样进入同版本checkpoint与严格restore；不能只把新字段丢掉、默认回填旧档或规划迁移。客户端快照缓冲是派生呈现状态，随场次／席位代次／销毁清空，不必持久化。

## 四 原始技术资料及本项目采用范围

### 4.1 Godot 固定物理与显示插值

[Godot官方说明](https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/physics_interpolation_introduction.html)区分固定物理tick和可变渲染帧，并介绍保留前后transform进行插值。本项目借鉴“模拟与显示不同步时在显示层重建”的原则；仅打开Godot物理插值不自动解决4–7Hz网络样本，也不能修复本身超时的模拟。

### 4.2 网络快照缓冲

[Glenn Fiedler原文](https://gafferongames.com/post/snapshot_interpolation/)使用短快照缓冲，在稍晚的呈现时刻插值位置与方向，承认增加显示延迟以换取抗抖动。它还讨论包含端点速度的Hermite插值。适用推断：本项目先评估有界时间缓冲和线性／角度插值，不直接采用可越界的自由样条；物理惯性与网络插值是不同职责。

### 4.3 赛车的输入平滑与速度相关转向

旧PhysX HTML文档链接本轮实际返回404，不冒作已读。已改读NVIDIA原仓库的[控制头文件](https://raw.githubusercontent.com/NVIDIAGameWorks/PhysX/4.1/physx/include/vehicle/PxVehicleUtilControl.h)和[实现](https://raw.githubusercontent.com/NVIDIAGameWorks/PhysX/4.1/physx/source/physxvehicle/src/VehicleUtilControl.cpp)。其中定义输入上升／下降率，并按前进速度查最大转向量。

本项目借鉴“目标速度渐变、转向速率有界、急弯主动降速”，不是导入PhysX或照搬赛车底盘。机器人仍需在狭窄场地精确停靠与响应集火；不做漂移或长刹车距离。

### 4.4 前视跟随与几何净空

[CMU Pure Pursuit原始报告](https://publications.ri.cmu.edu/storage/publications/pub_files/pub3/coulter_r_craig_1992_1/coulter_r_craig_1992_1.pdf)的1.2、2.0与3.3节描述沿路径选前视点、求曲率再跟随，4.1节讨论前视距离的效果；本项目可借鉴速度相关、有限的前视距离。这里的建议是项目适用推断，不是原报告为本游戏证明安全。

[Godot导航几何说明](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationmeshes.html)强调路径中心与实体外形的区别。本项目保留当前身体／扫段净空合同，即使采用前视或圆角，也必须验证整个运动段；不因引擎存在NavMesh就重写导航。

## 五 最小分阶段建议

### 阶段A 先把网络呈现和瞬转拆清

主责M04呈现，关联M05／M14／M15／M19／M24。建议允许文件为实际消费者`expedition/expedition.gd`、`camp/camp.gd`、`treasure/treasure.gd`及既有`battle/unit.gd`；只有经根审证明共同采样语义时才提取小型呈现组件，不先造全局网络管理器。

- 记录每次接受快照的服务时间、接收monotonic时间与序号，保少量有界历史；以呈现时间选择包围样本，不每帧重新追最新目标点。初始缓冲时长应从当前各模式实际间隔和抖动取值，不能全模式盲设一个常数。
- 无后一个样本时短暂保持或受限处理，不无限外推穿墙；场次／席位切换、首次生成、复连、死亡／出局、合法瞬移要有明确snap/reset。
- 用最短角差平滑显示朝向；盾板和瞄准有规则含义，需限制显示偏差／延迟，并让攻击效果来自权威数据。不能让身体看向另一侧却按旧方向减伤。
- walking显示结合被接受的权威移动状态与呈现速度，避免追近最新点时反复切Idle；不能把冻结／失能画成继续行走。
- 关键风险：只对两个稀疏位置作直线插值，也可能在真实90度绕障中切角。第一版必须标明安全策略：若缺关键拐点样本，保守回到已知安全段／最新权威点；要真正连续过角，需利用可信路径／中间样本或明确新快照合同，不能在客户端复制一套业务规划后宣称安全。

本阶段可以先改善直线追赶／朝向突跳，不宣称已解决服务器硬折线路径，也不改变目标、伤害、占点或收费。仅客户端改动可避免为呈现试点重建当前后端，但必须按实际源确定。

### 阶段B 在现有合法路径内平滑跟随

主责M04 Sim／Field几何边界。先做可见直线段的冗余格点裁剪，再评估局部前视或圆角；保持原起点／合法终点、身体半径、每段静态及动态检查。前视距离受速度、弯角和可用净空限制，不能直接跨过障碍内侧。

可采用“安全路径走廊内的线段＋圆弧／受限曲线”或有限前视导向；曲线必须被保守验证并按已有安全推进消费。没有足够净空就减速、保留折点或原地转向，不能为了每条线都圆润而压缩身体半径。不能仅用无约束Bezier／Catmull-Rom把整串路点连起来。

这会改变合法实际轨迹、接敌时刻和身体交互，不是纯视觉等价。需单独批准Field是否改、重规划缓存如何复用、沿路目标是否仍精确接近、动态拥堵时如何失败。避障原子性／可达拒绝、同版本恢复、门柱和近战到达是必测项。

### 阶段C 轻惯性参数

权威目标速度可由距离与曲率共同限制，例如制动距离约`v²/(2a_brake)`、曲率限速与转向速率上限；以有界加速度接近目标速度，遇硬障碍仍安全停止。公式是设计工具，不是当前已实现功能或获批数值。加速／减速影响到达和战斗，必须由服务器持有；客户端不能为“惯性”自行越过已判停的位置。

| 底盘 | 建议的感觉差异 | 不能偷改的边界 |
|---|---|---|
| 履带 | 起步稍沉、可低速转向／原地转身，短而清楚的制动 | 不强制赛车式大转弯半径；不能破坏门口精确停靠 |
| 双足 | 响应更敏捷，朝向与步态有短过渡 | 不做轮胎侧滑；步态连续不等于权威位置越界 |
| 轻型／侦察轮式 | 较连续的弧线和速度相关转向，急弯减速 | 当前不具真实非完整车体约束，增加最小转弯半径是新的玩法取舍，需另审 |
| 盾板／重型装配 | 保留既有正面盾转速规则，考虑更有重量的显示 | 盾向、射程、伤害和已有最大速度不因视觉调参被暗改；加固锅炉已有减速不重复叠加 |

原型调参可先在独立同版本场景对比短时加速／较快刹停，不先承诺统一毫秒数。大幅惯性导致移动指令像延迟、到门后滑出范围或钻头无法贴近，都应判失败而不是“更真实”。

## 六 可复验诊断与验收指标建议

以下是测试选集建议，未执行且不是当前通过值。由test_lead按已签实际改动复用工具，不创建一套新的永久采样／资源平台。

### 6.1 先判别顿挫来源

同一个有限直线／直角绕障场景分别记录：server simulation elapsed与tick耗时、每个实际快照服务时间及到包间隔、渲染帧时间、权威pos与显示pos／heading、walking动画状态。用同一时间轴判断服务器停步、网络空窗、低通追赶、渲染长帧、动画切换各自发生时刻，不能只看平均FPS。

先复用当前已签性能证据中与本改动无关部分；不把已知118ms／1066ms长帧的未知因果自动归到寻路或本次修复。也不能把视频看顺当成网络／物理正确性证明。

### 6.2 必要场景

- 稳定直线：同样server轨迹，在30／60渲染采样下比较显示速度波动、停止抖动与位置误差；新加入或重连不得从原点飞来。
- 90度、连续S弯、窄门、门柱旁、短距离往返点选；有／无盾、四类底盘至少按受影响维度选择，不机械跑全地图。
- 单机及拥堵小队：动态阻挡、目标身体、钻头有效射程、停止／反向新指令；保持合法目标与失败原子性。
- 单调包序、乱序／重复／短丢包及恢复；两种模式不同发送间隔；出局／终局／场次切换清缓存。
- 若改变权威运动状态：同版本checkpoint恢复后相同输入和delta继续等值；缺／非法字段拒绝，不回填旧档；新增服务镜像与客户端绑定据真实改动登记。

### 6.3 通过指标应分开

| 维度 | 应记录／判定 |
|---|---|
| 连续性 | 直线稳态呈现速度的变异系数、近零停顿次数；与同源修前轨迹比较，不只报平均FPS |
| 响应 | 玩家命令即时反馈、ACK时间、可见运动响应、额外插值延迟分别列；不能把反馈指示器出现当机器人已行动 |
| 误差 | 显示与权威位置／朝向的P95和峰值、缓冲年龄、重连snap次数；阈值由试点和场地净空共同签定 |
| 几何 | 每个真实推进段无新增墙／门柱／身体侵入；曲线有净空边界；不能只验离散终点 |
| 决策 | 不改收费、席位权限、指令序号及胜负；权威轨迹变化时明确接受何种接敌／路程差异 |
| 成本 | 同场满编帧时、server步时／寻路查询数、快照字节与频率；不靠无限增频或每帧重算解决视觉 |
| 终态 | 只运行必要数量窗口／临时服务；保原证据后清理归属资源，不动当前负责人试玩实例 |

建议根审先批准阶段A的具体小型试点及观测边界，再据证据决定阶段B/C，不同时重写显示、导航、碰撞和服务器同步后只靠一段视频判定成功。最终产品应有轻微重量感且指挥跟手，真实几何与服务器权威继续优先。
