# Design

## Context

见proposal。负责人2026-11-13要求架构整改先于功能扩张，目标于2026-11-14恢复后该优先级保持。审计A01–A12是代表路径静态发现，已有M06真实性能失败另有证据。现有规则已要求OpenSpec、开发代理实现、test_lead独立验证及主代理签收，缺少实现前的具体边界合同。

## Goals / Non-Goals

**Goals:** 让下一项修改在写代码前就有明确位置、权威、依赖和失败边界；使整改能分块验收，且例外与未修项可追踪。

**Non-Goals:** 本change不更改业务行为、运行服务或构建；不搬全部目录、不删除所有Autoload、不强制Resource/事件总线/Repository或跨语言共用运行时。A01/A05实现及其规格各自建change。

## Decisions

1. **一个评审入口、按规模填写。** `docs/architecture-review.md`维护流程与可复制模板；简单修改可一段引用已有合同，复杂修改补调用/状态图。评审在proposal/design下保留，签收归主代理；工程表单不能替代代码证据。
2. **先归属和状态，再选目录与抽象。** `docs/module-boundaries.md`按权威路线图seq61列M00–M24入口及目标约束。模块编号是产品职责，目录是当前实现位置；同文件跨多模块不等于应复制实现。抽象仅服务当前已证的共享行为、失败语义或可独立组合需求。
3. **明确提交与组合。** 跨领域写入先定事务/提交所有者；场景由共同上层配置必要依赖、协调兄弟及释放。传输机制与领域收据/意图分开，不能用通用重试自动重发未知写操作。保留全球生命周期必须说明理由及边界，不机械删除Autoload。
4. **先正确性，再治理共享边界。** `docs/architecture-remediation.md`登记全部审计项、阶段出口和依赖；A01/A05优先形成可证合同，再推进A03/A10事务边界、A04规则契约和A06/A07/A11的纵向组合切片。A08/A09/A12明确职责与触发门，实际资产/发行验证按适用改动执行。性能既有失败不由重构推定修复。
5. **记录可执行的例外。** 历史债务需列当前调用、保留原因、允许的操作、不得扩张范围及复审触发点；不因“旧代码这样做”自动准许新依赖。实现发现新跨域写或生命周期变化必须先回评审。
6. **分工与准入可核验。** AGENTS和OpenSpec context链接入口。主代理审合同及边界，开发代理据签收实现，测试代理以真实反例独立审查、按改动选择验证，进度代理只引用签收。治理本身做文档与反例审查，不为文档改动开模拟器或全套游戏测试。

## Risks / Trade-offs

- 表单变成空话 → 必填实际入口、状态和失败出口，A01/A05试用，拒绝只按行数拆分或填“无影响”无依据。
- 一次整改扩成全盘重写 → 分阶段/独立change，只在已证明受影响边界内实现；无关新功能暂不派单。
- 把目标边界说成现状通过 → 当前实现入口、目标约束、已验/未验和例外分栏，审计事实原样保留并加后续入口。
- 跨文件抽取破坏提交顺序 → 提交/回执及领域不变量先形成合同，故障和恢复用本轮新数据独立验证。
- 重复维护规范 → 长期流程在architecture-review，模块定位在module-boundaries，整改状态在remediation；change与资料空间链接原文。
