## Decisions proposed

1. 首轮建议原生 Android 横屏、类型化 GDScript、Godot 4 稳定补丁版本。实际版本和对应导出模板一起锁定。选定手机上比较 Mobile 与 Compatibility 的色阶、阴影和帧时，再定渲染器。
2. 按功能组织 robot、battle、base、ui，每个功能的 .tscn、脚本与定义靠近存放。编辑器制作机器人宿主、炮塔、建筑、HUD、地图骨架。运行时按存档或装配单实例化 PackedScene；公开地图可程序选择节点和布局。父场景注入依赖、监听子场景信号；子场景不跨树查找主界面。全局仅保留确需跨场景的会话等服务。
3. Resource 保存共享只读部件定义；血量、归属、冷却和维修记录属于每台实体。服务器模拟和结算独立于相机、粒子、动画和 UI。导入 GLB 是视觉子场景，碰撞、插槽适配与玩法脚本放在 Godot 包装场景。沿用 Blender 米制、Z 向上、−Y 前向及 socket/ATTACH 配对；用左右不对称样板检查轴转换，不手调每个实例补偏差。共享资产 ID、组件 ID、机器人实例 ID 分开，网络只传已注册的 ID。
4. 建议两条通信路径：HTTPS 负责登录、背包、编队、房间分配和历史；原生客户端用 ENet/UDP 连 Godot 无窗口权威战斗进程。首版单部署区域、一个持久化业务服务和数据库，房间不直接改玩家余额。会话以短期、限房间凭证绑定玩家席位。公开营地日程以服务器时间为准。
5. 可靠指令携带序号，服务器校验归属、费用、目标和冷却；位置与朝向用可丢弃的有序快照，客户端插值。生成、销毁和最终结果走可靠消息；不同通道隔离。先试模拟 20 Hz、状态 10 Hz，不做全局确定性锁步；以操作迟滞、单房带宽和手机帧时决定是否调整。重连先取全量基线，再接增量；客户端资源版本不符拒绝入场。
6. 房间以 battle_id、机器人实例 ID 和事件序号生成战斗时间线。持久化服务按唯一战斗结算键提交资产、归属和战绩；重发时返回已有结果。房间进程中断且无有效最终结果，原型按无结果解除任务锁，不发胜利奖励。服务器已提交的结果以账本为准。

## 验收样例

单独运行机器人展示场景，替换部件、重导 GLB 后挂点和逻辑仍有效。两客户端围攻一台目标；其中一台断网、重连，双方胜负一致，重复投递结果仍只有一笔结算。用快照乱序、丢包与手机切后台复测。独立记录帧时、带宽、指令到可见反馈时间及峰值单位数。

## Open Questions

已确认：首轮从 Godot 编辑器 Debug 启动两个独立客户端，本机容器运行独立权威服务端；第二轮用 Android 真机连接同一服务。主代理负责独立操作、核对日志和汇报结果。具体手机型号在真机复验时记录；公网区域、预算与其他平台另议，不阻塞本地测试。

第一轮用不同测试身份进入同一房间，分别下令，关闭并重连其中一个客户端，对照双方状态与服务端事件。桌面客户端连接宿主机映射的 UDP 端口。第二轮把其中一端换成同局域网 Android 手机，连接宿主机局域网地址，验证触控、后台恢复与重连。两轮分别留存构建版本、客户端画面与同一房间日志，不以桌面通过代替真机通过。

负责人更新首测顺序：桌面双窗口之后先用安卓模拟器验收。当前使用 API 35、硬件 GPU 的虚拟设备，完成模拟器阶段即可继续研发；实体手机型号、触指遮挡、发热与发布性能预算放在后续设备验证。此决定取代上文的原首测顺序。
