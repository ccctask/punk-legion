# Design

## Context

见proposal。交付对象以`build/private-beta/current-playable.json`定位：正式客户端1077、515冻结源及原r2实际后端分开。当前源目录可能含未交付差异，不能以工作树代替已签包。原r2四份操作文件为锁定历史交接，不编辑。

## Goals / Non-Goals

目标是可追溯的完整出口矩阵与准确运维说明。每项要求可追到原策划/路线/规格、当前实现范围、具体独立签收及其适用依据；缺少证据保持缺口。只审文档和文件，不执行游戏或环境验证，不将静态文档整理视为新的功能/性能测试。

## Decisions

1. 进度代理从原策划及路线列M00–M24与负责人关键决定，落本change的`verification/requirements-matrix.md`，每个模块有原要求、当前能力、权威主验、适用性/缺口。额外用原设想五点及后续已决参数检查无遗漏。原资料页不新建重复项目。
2. 开发代理维护`docs/current-playable-delivery.md`及通用运维手册的适用性标记，依稳定索引/实际脚本核启动、身份、健康/监控、诊断、账号恢复及停止入口。历史迁移/恢复/回退明确不属于当前日常流程；代码与冻结Ops不改。未配置/未运行的监控或权限服务不能写成已部署。
3. 测试代理独立审矩阵与手册，优先当前已签完整链/依赖不变证据。将“当前原生实测”“已核相关依赖可继承”“只有历史证据/当前适用未证”“明确失败”“外部观察待验”“用户明确后续范围”分开；每个继承声明写实际生产/包/环境及依赖依据。入口存在、源码合理、change归档或同协议都不能单独证明完整行为通过。只读脚本先查迁移夹具，禁止执行。
4. 新发现缺口按玩家影响/变更依赖形成最小后续清单。审计不授权新测试或开发；root审查后再给具体范围。性能无可信热点时不立虚假优化，不降低33.333ms门槛、不将静态微优化换算FPS。
5. root独立签任务，进度代理仅引用本次结果更新原总览/阶段/看板。采用单一矩阵和简明手册，不复制所有历史日志或新建测试框架。

## Risks / Trade-offs

- 旧验收覆盖有限、相关共享源后来变化 → 显式标出当前未证行为与最小补证，不泛称所有旧证据失效，也不以文件名/root前缀冒充签收。
- 当前客户端/后端编号不同 → 以稳定索引分开核包源与服务实际源，r2 source/image不被rc1077替代；六ID为历史激活记录而非新的在线证明。
- 老运维命令误操作共享/试玩实例 → 当前维护入口优先，历史示例标注不可直接执行，清理仅精确实例，默认不删卷；本轮零运行资源。
- 只完成证据审查仍有M06/人体验缺口 → 任务签收限于本项文档，不把整款目标改成“审计完成”。
