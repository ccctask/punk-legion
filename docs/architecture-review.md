# 功能实现前的架构评审

状态：生效流程；2026-11-14建立，2026-11-15补派单启动核验；维护：主代理。适用：新增功能、缺陷修复、结构调整及会改变产品依赖的工具接入。依据[协作规则](../AGENTS.md)、[工程规格](../openspec/specs/engineering-baseline/spec.md)、[审计事实](architecture-audit-2026-11-13.md)；模块定位见[边界表](module-boundaries.md)，当前整改见[台账](architecture-remediation.md)。

## 何时必须做

创建OpenSpec change并核对需求后、派开发实现前完成。需求已确认不等于实现位置和提交语义已确认。只读调查、范围讨论与提案可先进行；关键边界未定不得开始实现。简单修改可在design或任务卡写一段完整记录，复杂修改补状态表/依赖图；不要求每次另建一套文档。

产品代码、测试工具、自动化编排和临时辅助代码均适用（2026-11-15负责人重申）。先查已有组件及其真实调用者，说明复用或新增的理由，避免复制资源所有者、状态机和业务规则。工具的执行权限与资源收尾同样属于生命周期合同。

主代理维护需求/范围和签收；可委派只读评审；开发代理解释实现与复用取舍，不自签；test_lead给独立选集和验证限制；进度代理链接权威记录。沿已有产品决定，常规技术取舍由主代理定案；涉及新的产品目标或无法消除的关键歧义才向负责人讨论。

派新任务或退修先核接手代理状态。已完成的代理须使用能触发新轮的派单方法（当前为followup_task）；send_message只传消息，不算启动。以接手回复或实际工具句柄核实执行，不能把“已发消息”、计划文件或旧running记录当正在运行；状态询问不得重复启动已运行的入口。等待具体Job时沿同句柄，减少无任务等待与重复复现工装。

## 必答内容与模板

复制到对应change的design或`verification/architecture-review.md`，不得只填“按规范”“无影响”。

```text
状态：草案 / 待补边界 / 通过 / 带约束通过
日期、评审源/哈希、主代理签收：
玩家问题、规格/审计项、主责Mxx、关联模块、当前里程碑：
当前入口与调用链；已存在的组件/机制及其实际证据：
状态所有者：客户端临时状态 / 权威状态 / 持久化 / 账目 / 公共定义：
功能归属与归并：模块负责/不负责什么；功能为何应写在此处；哪些共享不变量/生命周期/变化原因要求放在一起，哪些需要分开：
依赖方向：谁调用谁、通过什么入口、谁创建/配置/释放：
完整生命周期：创建→配置→运行/暂停/恢复→失败/重试→销毁；各阶段谁推进/释放，外部借用状态如何处理：
行为合同：成功提交点、失败/未知结果、取消/离页/重连、重复操作：
抽象与组合：保留/复用/提取哪一项、真实共同语义与有意差异、备选取舍：
允许改动的文件/接口/状态；禁止附带范围；兼容与运行版本影响：
验收：可观察断言、故障和恢复、新数据来源、复用/省略依据、资源预算：
保留例外：当前耦合、理由、约束、后续负责人、复审触发条件：
未决项及处理；通过后允许派哪些任务：
```

没有可变状态或持久化时可注明不适用并给理由；不发明空抽象填表。小修改可引用同模块已签合同，并明确本次哪些依赖未变。涉及公共入口、跨域写、继承或场景释放时不能仅以“只改几行”简化关键分析。

### 实现落位清单

2026-11-15负责人再次要求：评审必须能指导实际代码落位，而不只是说明功能值得做。在上述记录中，按本次新增或改变的职责填写以下清单；同一合同下的小修改可合为一行，无须逐函数造表。

| 本次职责与明确不承担的职责 | 所属模块及实际文件/场景入口 | 放在这里的依据、复用或组合方式 | 状态所有者与创建/运行/恢复/释放方 | 上下游依赖及允许调用入口 |
|---|---|---|---|---|
| 填本轮实际行为 | 填真实路径 | 填当前不变量、生命周期或变化原因；说明为何不合并或拆分 | 无状态时说明理由；异步回调说明失效条件 | 标明方向，不以能访问对象代替调用合同 |

主代理据此决定哪些职责应同处、哪些通过组合协作、哪些必须分离，并将结论写入签收。若无法解释功能为何属于所选入口，先补调查或调整方案，不先往现有大脚本里追加代码。开发交付对应此清单说明实际差异；新增状态、依赖或职责超出清单时，按下文复审。

## 边界判断

| 关注点 | 需要确认的合同 | 需要退回的情形 |
|---|---|---|
| 模块位置 | 主责模块拥有此业务概念；关联模块经明确入口协作 | 因为某脚本方便访问就把另一领域写入放进去 |
| 合并或拆分 | 按当前共享不变量、生命周期、变化原因和依赖方向决定同处、分离或组合；保留必要原子编排 | 先堆代码再补架构、按长度拆文件、名称相似即合并，或把本应同事务的规则拆散 |
| 状态与提交 | 内存/权威/磁盘/收据分别由谁拥有；何时可确认或发布 | 内存先变、存盘失败，仍通过其他路径发布“成功” |
| 跨域事务 | 编排入口、同事务不变量、排序、鉴权/到期/失败语义 | 拆文件或加通用层后改变账务原子性，未说明影响 |
| 场景组合 | 上层初始化依赖并协调兄弟，局部组件可独立验证 | 子场景依赖未登记的父/兄弟内部路径，退出后残留回调 |
| 抽象复用 | 至少有当前真实共享合同，或明确的隔离/测试/组合价值 | 按行数拆、为未来猜想造框架、把不同玩法硬塞同一规则 |
| 公共数据 | 定义的单一权威、版本/生成契约、可变实例隔离 | 多语言复制数值无校验，或修改缓存共享材质影响其他实例 |
| 传输与领域 | 传输管理请求/回调；业务解释意图、收据和权限 | “通用重试”重发未知写、失败GET后自动执行过期意图 |

## Godot 与服务端约束

固定功能界面和可复用实体优先用`.tscn`组合；动态机体实例、列表项和特效可正常实例化，不要求把所有内容预放场景树。模型导入场景保视觉来源，玩法宿主/模块包装保身份、挂点和接口。外部依赖可通过初始化参数、导出引用、Callable或明确服务接口提供；信号报告事件，上层负责协调与释放。全局会话确需跨场景存活时允许Autoload，但不能因此获得任意业务状态写权限。

规则模拟不依赖渲染节点；共享定义可用JSON/常量/Resource，选择取决于权威和编辑流程，不强制改格式。共享可变资源须明确复制或实例隔离。继承前核父类状态机、成员名、覆盖点和失败路径，不能只看方法签名。

服务端路由/用例负责编排已定义业务入口；领域持有自身不变量，持久化和传输机制不决定产品含义。需要同事务的库存、生产、设施、任务和战果保持显式编排；先核真实时序再抽取，不机械新增Repository、后台调度或跨语言统一引擎。

这些选择参考[Godot场景组织](https://docs.godotengine.org/en/4.6/tutorials/best_practices/scene_organization.html)和[Autoload使用边界](https://docs.godotengine.org/en/4.6/tutorials/best_practices/autoloads_versus_regular_nodes.html)，具体生效要求以本项目规格与已签评审为准。

## 签收与复审

只有主代理写明“通过”或“带约束通过”、可实现范围及依据后才派开发。带约束通过的例外必须有理由、影响、约束和触发点；未知提交所有者、权限或失败语义不能作为例外绕过。实现新增跨模块依赖、改权威/提交/生命周期或需要额外公共抽象时，先交差异并复审，再继续该部分实现；不重做无关已签分析。

派单附已签评审的准确链接、获准模块/入口和生命周期所有者，接手代理先核后写。没有记录或实际实现需要越界时，报告具体缺口并暂停相关部分。交付说明逐项对应实际归属、依赖和生命周期，解释新增代码、状态或抽象为何必要；功能通过不能替代结构验收。

验收时比较实际差异与评审范围，检查新增依赖和状态写入、组件组合、失败/恢复、测试有效性与资源收尾。越界部分退回原实现方。架构评审通过、开发自测、正式验证、主代理签收和当前试玩版本分开登记。原审计风险只有对应证据充分时才能关闭；文档完成不能把风险改成已修复。
