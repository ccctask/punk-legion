# 一 已确认的研发边界

| 项目 | 研发基线 |
| --- | --- |
| 美术 | 可爱工业玩具风，场景与机器人遵循blender-pikachu-diorama规范 |
| 资产工具与引擎 | Blender制作源资产，Godot实现运行时；具体版本与移动渲染方案待技术讨论 |
| 机器人 | 模块化装配、自定义名字、机体收藏、参战场数、击败敌机数与为友机实际恢复的耐久；当前不做性格和对话 |
| 战斗 | 即时小队战术，基础行为自动执行，玩家少量手动指挥 |
| 轻度路线 | 私人基地经营与单人或组队PVE探索，主要日常15至30分钟 |
| 重度路线 | 可占领营地，服务端统一开放时段，玩家实时参战，无轻度离线保护 |
| 战败 | 机器人身份及已拥有部件保留，维修恢复，公开营地可失守 |
| 商业模式 | 外观收费与轻量道具收费，具体道具范围待定 |
| 团队 | 个人与AI，优先可重复构建、数据驱动与小规模可玩版本 |

公开玩法的两条路线分别是“可占领的实时竞争营地”和“不可永久占领的组队PVE探索”。它们共享机器人与基础战斗系统，风险和参与节奏分别设计。私人基地受控野生袭击的离线恢复规则继续保留，不延伸为公开营地保护。

# 三 通用验收与任务模板

每个模块包含明确的操作入口、最小可演示内容和可观察结果。正常流程需要演示；涉及资源、归属和网络的模块必须验证失败、重试与重复请求。低风险展示调整以人工检查为主，关键规则用自动化回归保护。

模块状态使用“待开始、进行中、待验收、已通过、阻塞”。AI负责实现、自检和整理证据，项目负责人体验关键流程并确认玩法、美术与范围。发现缺陷后记录具体复现步骤和结果，不以“基本完成”代替验收。

每次验收记录工程版本、构建版本、运行环境、操作步骤、实际结果、日志或录屏、遗留项。未通过的条目保持可见。性能结论必须包含设备、分辨率、同屏数量、光影设置与持续运行时间。

后续从模块拆出的单张任务卡采用以下内容：

- 所属模块、当前状态、前置依赖与本轮目标。

- 明确交付物，以及本轮不包含的扩展范围。

- 可逐步执行的验收步骤、预期结果与失败条件。

- 测试环境、实际证据、遗留问题与完成日期。

# 四 阶段A 技术与资产样板

## M00 工程盘点与技术基线

依赖：无。交付：已有项目清单、目标设备清单、Godot与Blender版本记录、最小技术约定，以及后续规范的待决项。

验收：

1. 区分已有可用内容、需验证内容和缺失内容，记录运行入口；不以文件存在判断功能已完成。

2. 确定首个验收移动平台、至少一台实际测试手机与屏幕方向。另一移动平台单独排入渠道验收。

3. 为渲染、语言、服务端形态和素材导出各记录选择与验证方法；未经讨论的版本号和性能指标不写成既定要求。

证据：工程清单、基线记录与可复现的启动步骤。此模块是下一轮技术讨论的主要入口。

## M01 Godot工程骨架与最小构建

依赖：M00。交付：主入口、测试场景、基础配置加载、日志、开发构建与移动安装流程。

验收：

1. 从干净检出按记录步骤启动客户端，并导出安装到首台目标手机。

2. 手机进入测试场景、正确接受触控、切回前后台后不重复创建游戏会话。

3. 缺失配置有明确错误；开发环境配置与发布环境区分，工程不包含真实服务密钥。

证据：启动录屏、安装包与构建日志。此时允许灰盒，不建设大型通用框架。

## M02 Blender到Godot资产样板

依赖：M00、M01。交付：一台原创机器人、两件可交换模块、一段场景地块、一座建筑和一座固定炮塔的最小样板；保留可编辑源文件、生成配方、实际导出物与导入场景。

验收：

1. 依照blender-pikachu-diorama检查短胖轮廓、色块、2至3档明暗、纹样与接触关系；场景植物有真实轮廓变体，不能只旋转同一模型。

2. 在Godot内核对比例、朝向、原点、接口位置、活动轴、颜色和阴影。机器人本体不混入展示地台、标注或参考对象。

3. 从保存的Blender文件重新打开、重新导出，再次导入后结果一致。材质使用目标引擎中已验证的表达，不能用白模代替风格通过。

4. 动画范围至少包含样板机待机、移动、攻击和停机，检查起中末帧、循环与模块连接；每项动作单独记录通过情况。

证据：Blender与Godot同视角截图、实际导出物多视图、动画录屏、导出统计与性能审查报告。几何预算检查和目标设备运行检查分开记录。

本机规范来源为 `C:/Users/alienware/.codex/skills/blender-pikachu-diorama/SKILL.md`，并结合其风格指南、性能审查与本地模型库发布流程。正式资产按现有模型库流程准备、视觉审核和本地入库；试验草稿明确标记，不冒充已发布资产。

## M03 模块数据与装配合法性

依赖：M02。交付：底盘、核心、武器与功能模块的数据定义，插槽描述，统一装配校验器，以及少量有效和无效样例。

验收：

1. 两件兼容部件可替换，效果和最终指挥点同步改变。

2. 错误接口、超重、超功率、散热不满足、功能互斥与重复部件占用分别给出明确原因。

3. 同一套数据生成的编队在客户端预览与服务端校验结果一致；修改本地数值不能绕过服务端规则。

4. 缺失或不兼容的配置版本明确拒绝加载或进入迁移路径，不静默使用错误默认值。

证据：装配样例清单、规则回归结果与预览截图。首轮不做任意物理拼接。

# 五 阶段B 战斗与联网验证

## M04 单机战斗与小队指挥

依赖：M01、M03。交付：一张灰盒战场、基础移动与索敌、移动和集火指令、一个主动技能、胜负与撤退规则。

验收：

1. 玩家可完成选择、移动、集火和撤退；短时不操作时单位继续执行基础行为。

2. 机器人不穿过禁止区域，多个单位堵路时有可观察的处理，不持续卡死。

3. 分别测试12台轻型与6台重型等预算编队，确认费用、台数和目标进度正确。

4. 维修有储能或规则上限，超时按目标结束战斗，不出现无限拖局。

证据：完整战斗录屏、关键状态日志和阵容配置。首轮只需少量武器与一种目标玩法。

## M05 双客户端与权威战斗房间

依赖：M04。交付：独立权威进程、两个客户端、入场校验、指令同步、状态同步、断线重连和临时结算结果。

验收：

1. 两个客户端连接同一房间、操作各自单位，对目标、伤害和胜负得到一致结果。

2. 发送越权操作、非法装配、重复指令与修改后的客户端数值时，服务端拒绝并记录原因。

3. 一端断网再连接，恢复当前状态；超出重连窗口按明确规则处理，不复制单位或重开奖励。

4. 服务端停止或房间异常有失败出口；客户端不能自行宣布胜利并领取资源。

证据：双端录屏、权威进程日志和异常测试记录。此阶段使用测试身份与临时结果；持久化账户和经济结算由M07、M08完成。

## M06 手机表现与战斗规模验证

依赖：M02、M05。交付：目标手机上的真实资产战斗、性能基线与操作结论。

验收：

1. 在记录的设备与画质下，演示标准约24台单位战斗、密集技能与接触阴影，测量帧时间、内存、发热和加载。

2. 测试小队选择、技能提示、遮挡和手指覆盖，远景可分辨底盘与主武器。

3. 在预设弱网场景记录指令延迟、同步异常和重连表现。

4. 与M00确定的体验目标比较；不达标时减少材质成本、效果或同屏预算，再用同场景复测。

证据：实机录屏、测量数据与调整前后对比。通过这一关才冻结首轮资产预算，不承诺所有手机通用性能。

# 六 阶段C 私人经营闭环

## M07 账号 机器人身份与持久化

依赖：M05。交付：测试账号登录、账户数据、唯一机器人身份、任务状态与持久化版本。

验收：

1. 两个账号的数据隔离，重启客户端与服务端后机器人归属和任务状态一致。

2. 同一机器人不能同时出征、驻防、援助和维修，失败请求不会留下永久锁定。

3. 旧数据可迁移或明确拒绝不兼容版本，测试备份可恢复。

4. 变更登录会话后，前一会话不能继续越权修改资产。

证据：重启与恢复记录、权限及互斥测试。正式渠道登录接入在M23处理。

## M08 资源背包与唯一结算

依赖：M07。交付：资源账本、实体部件库存、蓝图权限、奖励与消耗结算。

验收：

1. 制造、入场与奖励各有唯一业务标识，重复点击或网络重试只生效一次。

2. 资源不足时操作完整失败，不出现扣了材料却没有产物。

3. 战斗结果重复提交、延迟到达、结算中断后重启，最终只发一份奖励。

4. 服务端能按业务标识查清资源变化；客户端伪造掉落不生效。

证据：正常、失败、并发与重启情况下的前后账本。核心资源操作必须有回归测试。

## M09 装配车间与实体制造

依赖：M03、M08。交付：装配界面、方案保存、材料制造、部件拆装、实体机体预览。

验收：

1. 保存方案后制造实体，得到独立身份；同方案的两台机体互不覆盖。

2. 拆换部件正确归还库存，已装配部件不能再装到第二台机体。

3. 制造与改装后重登，机体、库存与费用一致。

4. 非法方案在界面有明确原因，服务端也拒绝制造。

证据：制造至改装的录屏、库存对账与重复请求测试。

## M10 机器人档案 三项服役累计

依赖：M05、M07、M08。交付：自定义命名、机体收藏与按永久编号归属的三项累计。

验收：

1. 同一台机器人改名、换装后，累计值和收藏仍归原机；同名机体分别统计，新机显示三个零。

2. 一场已知脚本战斗的实际参战场数、末击击败敌机数、为友机实际恢复的耐久逐项核对。

3. 对满血目标的无效维修不计入有效输出；同一战斗重连与重复结算不重复累计。

4. 受修、平台维修、指挥官急修和战后工坊修复均不计入机体的维修贡献。

证据：权威结算、预期与实际三项累计、重发同一结算的对账及同名机体的档案截图。玩法战报继续提供个人结果、奖励与维修报价。

## M11 私人基地网格与建筑

依赖：M01、M07、M08。交付：建筑放置、移动、占地与道路、简化供能、保存加载。

验收：

1. 可放置核心、生产、仓库、装配、维修与炮塔样板；重叠、越界和缺少必要连接均有提示。

2. 移动建筑后占格、通行和供能同步更新，重登布局不变。

3. 基地入口和任务关键位置不可被不可恢复地封死。

4. 袭击锁定后调整的战斗布局按规则在下一场生效。

证据：布局操作录屏与保存加载对比。暂不做复杂多资源管线模拟。

## M12 生产 科技与离线收益

依赖：M08、M11。交付：三种通用资源生产、有限科技解锁、离线产出与仓储封顶。

验收：

1. 按已知时间跨度计算产出，短时、24小时、超出封顶时间分别对账。

2. 修改手机时间、反复登录与多端领取不增加额外收益。

3. 仓库满后停止累积，不倒扣；离线3天与7天不造成额外资产倒退。

4. 科技解锁有限功能与蓝图，不产生无限叠加属性。

证据：时间测试、经济模拟与服务端账本。使用可控制的测试时钟，避免验收必须真实等待数日。

## M13 维修 回收与恢复保障

依赖：M08、M09。交付：战损状态、修理队列、回收收益与最低可玩小队救援。

验收：

1. 战败后机体与部件仍存在，损坏机不能无条件再次出战，维修完成后可用。

2. 资源扣除、队列完成与重登恢复一致；重复领取不增加材料。

3. 制造、维修、回收循环不会净生成资源；救援配额不可转让和反复刷取。

4. 账户耗尽常规材料时仍有受限途径恢复最低可玩小队。

证据：失败账户恢复录屏与成本核算。

## M14 单人探索与掉落闭环

依赖：M04、M08、M09、M10、M12、M13。交付：一个探索区域、资源节点、一个首领、部件或蓝图进度奖励。

验收：

1. 完成“生产、制造、编队、探险、结算、维修、改装、再次出征”整条流程。

2. 胜利、失败、撤退与中途断线分别得到正确且唯一的奖励和战损。

3. 稀有奖励具有可检查的保底进度；基础成长无需通过PVP。

4. 连续试玩三轮能够发现至少一种有意义的部件替换，而非只增加数值。

证据：端到端录屏、随机与保底测试。阶段C出口是一套可保存的私人经营闭环。

# 七 阶段D 轻度联机版本

## M15 组队PVE探索

依赖：M05、M06、M14。交付：邀请、准备、入场与协作目标；先验收2人，再扩展至最多3人。

验收：

1. 各玩家只指挥自己的小队，全队按房间预算入场，机器人不能重复占用。

2. 队长退出、队员断线与重连有明确处理，不让其他玩家永久卡在房间。

3. 各自奖励、战绩与维修独立正确结算，不能窃取队友已有部件。

4. 3人版本单独复测同屏单位、敌人波次、目标手机表现与等待时间。

证据：双人和三人协作录屏、异常日志与实机记录。探索区域不可永久占领，不混入强制PVP。

## M16 私人基地野生袭击
